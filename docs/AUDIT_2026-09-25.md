# Self-audit, 25 September 2026

The external audit of 17 September (`docs/RESEARCH_AUDIT_2026-09-17.md`)
refuted this project's first relational rule and found four implementation
bugs. The repair that followed — "billing signatures" — was the project's
central contribution until this audit. This document records how that repair
was itself refuted, what else was found, and what replaced it. Every
counterexample is in `audit/2026-09-25/` and is re-checked by experiment E0 of
`bench/evaluate.py`.

The standard applied is the one the brief sets: if an experiment contradicts a
stated property, the property is wrong, not the experiment.

## Summary

| ID | Finding | Severity | Status |
|---|---|---|---|
| F1 | Billing signatures compare request *sizes*; real tokenizers bill equal-size text differently | Soundness, conceptual | Rule replaced |
| F2 | A provider's output length depends on request *content*; equal-size requests are answered differently | Soundness, conceptual | Rule replaced |
| F3 | Signatures compare models, prompts and variables by *local name*; a redeclaration inside one arm is invisible | Soundness, implementation | Fixed |
| F4 | The runtime keyed its invoice by local name, not the provider's model | Evaluation validity | Fixed |
| F5 | The runtime drew output lengths independent of content and billed with the analysis's own estimate, so it shared the rule's blind spot | Evaluation validity | Fixed |
| F6 | Token counts are not subadditive; `tokens(template) + Σ tokens(argument)` is not a bound | Soundness of the unary bound's premise | Bound rebuilt on bytes |
| F7 | A response re-encodes to more tokens than were generated, under the same tokenizer | Soundness of chained input bounds | Bound rebuilt on bytes |
| F8 | `tokens ≤ bytes` fails for SentencePiece, NFC and NFKC tokenizers | Soundness of any byte-based contract | Per-tokenizer contracts |
| F9 | (In this audit's own new code) reordering calls inside a retry body for the bill observer | Soundness, implementation | Fixed before release |
| F10 | `chars/4` is documented, `bytes/4` is implemented; both are exceeded on most non-English text | Documentation, estimate quality | Documented; estimate kept as an estimate |

## F1 and F2: comparing sizes is the same mistake as comparing bounds

The v3 rule abstracted each arm of a secret-guarded branch to a sequence of
`Call(model, sizeTerm)` nodes, where the size term was the estimated token count
of the template and literal arguments plus symbolic lengths of variables. Two
arms were accepted when their signatures were equal.

Equal *sizes* do not mean equal *bills*, for two independent reasons.

**Tokenizers.** Size terms were computed with the compiler's estimate, `bytes/4`.
Real tokenizers do not bill strings of equal estimated size equally. `"aaaa"`
and `"bbbb"` are both one estimated token, and are one and two tokens under
r50k_base; across 14 real tokenizers, 84–92% of randomly drawn pairs of
equal-length strings have different token counts (`bench/results/tokenizers.json`,
Q7). And even an *exact* token count would not help, because of F2.

**Providers.** A model's output length depends on what it is asked.
`bench/provider/measure.py` runs a real instruction-tuned model
(SmolLM2-135M-Instruct, pinned revision) on pairs of chat requests padded to
*exactly* equal token counts under the model's own tokenizer and chat template.
Under a shared sampling seed, 15 of 15 pairs gave different output lengths
(mean difference 34 tokens) — including all 9 pairs whose instruction was
identical and only the ticket text differed.

**Counterexamples.** `audit/2026-09-25/equal_size_literal.orch` and
`equal_size_template.orch`. The v3 rule accepts both. Under the runtime with a
content-dependent provider or the content-sensitive tokenizer, the bill moves
with the secret; E6 re-bills the requests with real tokenizers and
`equal_size_template` differs under r50k_base, cl100k_base and o200k_base even
with the provider held fixed.

**Why it is the same mistake.** The withdrawn equal-bounds rule compared a
maximum where a value mattered. The size rule compared a size where the content
mattered. Both compare something coarser than what determines the observation.
`docs/FORMAL_MODEL.md` Theorem 6 makes this precise: *any* analysis whose verdict
depends on text constants only through a size measure is, for content-dependent
providers, either unsound or forced to reject a branch whose two arms are
identical.

**Replacement.** Requests are compared by content: model identity, template and
literal text exactly as sent, bindings by identity, and earlier responses by
position (`src/relational.cpp`). Equal signatures mean identical requests, so no
observer of the transcript can distinguish the arms, under any tokenizer
(`docs/FORMAL_MODEL.md` Theorem 1).

## F3: names are not bindings

`audit/2026-09-25/shadowed_model.orch` redeclares `m` inside one arm as a
different, 100x larger model; the v3 signature for both arms read `m(in=…)`
and was accepted. `shadowed_prompt.orch` does the same with a prompt of equal
estimated size and different text. Both leak under the runtime.

Audit finding 4 of 17 September was the same confusion in the *runtime*. It was
fixed there and not in the relational pass, which resolved names independently.

**Fix.** The semantic pass gives every declaration a unique binding id and
records, per call site, the endpoint identity (provider, model name,
`max_tokens`, byte cap) and the template text. The relational pass never looks
at a name. A third case, an *input* redeclared inside an arm, turned out to be
ill-defined rather than leaky — whether it leaks depends on how an environment
supplies two declarations of one name — so the language now rejects inputs and
secrets outside the top level (`E203`).

## F4 and F5: the checker shared the blind spot

The runtime drew every output length uniformly from `[0, max_tokens]` regardless
of the request, and billed input with the analysis's own per-part estimate.
Those are exactly the assumptions under which the size rule is sound, so the
paired experiment could not have caught F1 or F2. E5's column
`old_harness_sees_it` measures this directly: of the leaks the size rule
accepts, the previous harness configuration sees none except where the model
differs.

It also keyed the invoice by local name (F4), which would have hidden F3.

**Fix.** Values carry text. The provider can be made content-dependent. Its
randomness can be coupled three ways (by event, by model, by request). Input can
be billed by a content-sensitive tokenizer that, like real ones, is not
subadditive. The invoice is keyed by the provider's model name. `run --json`
emits the full transcript, and the harness checks every relational verdict in
every combination and re-bills requests with real tokenizers.

## F6–F8: what a token bound can rest on

Measured on 14 tokenizers pinned to exact revisions, over every Unicode scalar
value, 388 UDHR languages, CPython source and CLDR JSON
(`bench/tokenizers/measure.py`):

* **F6.** `tokens(u·v) − tokens(u) − tokens(v)` reaches 3–6 in every
  tokenizer; `" Attribute"` and `"profiles"` are one cl100k token each and
  `" Attributeprofiles"` is six. About 1–2% of random concatenations exceed the
  sum of their parts.
* **F7.** Decoding a generated token sequence and re-encoding it with the same
  tokenizer gives up to 9 tokens per generated token (Qwen2.5). Over random
  generated sequences the worst ratio ranges from 1.03 (T5) to 9 across
  tokenizers; a single vocabulary entry re-encodes to 3–9 tokens. The compiler
  used a model's output cap directly as the next call's input bound.
* **F8.** `tokens(s) ≤ bytes(s)` fails for SentencePiece tokenizers (a dummy
  prefix no byte pays for), for Qwen2.5's NFC normaliser (U+0FAC: 3 bytes, 6
  tokens), and for T5 and XLM-R's NFKC-like normaliser (194 more tokens than
  bytes on one string).

**Fix.** The guaranteed input bound is built from bytes, which do add up and do
not depend on the tokenizer, and converted once per request through a
per-tokenizer contract `tokens ≤ κ·bytes + σ` justified structurally
(`bench/tokenizers/contracts.py` generates `src/tokenizer_contracts.cpp` and
refuses a contract the measurement contradicts). T5 and XLM-R have no such
contract, and the compiler refuses to certify a guaranteed bound through them.
A response's byte length is bounded by `λ × tokens`, with `λ` the most bytes one
vocabulary entry decodes to, or by a client-side byte cap.

## F9: a bug in this audit's own code

While writing the soundness argument for the bill observer
(`docs/FORMAL_MODEL.md` Theorem 3), it became clear that reordering calls is
unsound inside a retry body: an attempt's success is decided on its transcript,
whose order a validator may depend on. The intermediate v4 build did reorder
there. `audit/2026-09-25/retry_reorder.orch` was accepted, and the runtime
showed 1 attempt against 3 under the same seed. Fixed before release; the
counterexample is a regression test.

It is recorded here because it is the same kind of error as everything above,
made while fixing everything above.

## What survived

* The unary output bound, and the componentwise treatment of branches.
* The flow type system, with one deliberate relaxation (OP-1): `E230` now
  applies to secret *content*, so a value computed inside a secret arm from
  public data may reach a prompt. Thirteen adversarial attempts to abuse this,
  and two cases the relaxation must allow, are tests in `tests/tests.cpp`; each
  attempt is caught.
* All five counterexamples of 17 September (E0).

## What this audit did not do

It did not audit the flow-policy half (E8) beyond re-running it, did not test
against a hosted provider, and did not verify the C++ against the formal model;
the Coq development in `proofs/` covers the model, not the implementation.
