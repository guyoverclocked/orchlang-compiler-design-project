# Structured scalability study preregistration

**Registration state:** fixed before timed runs. Generated inputs and their SHA-256 inventory will be frozen in `output/scp_strengthening/scalability/inputs/` and appended below before the measurement command is run. Any post-freeze input change invalidates this registration and requires a new hash inventory.

**Question.** Which parts of the exact all-finite-horizon success-only usage-law pipeline dominate work as graph structure, finite kernel support, visible usage alphabet, and reachable stochastic state count change? The study is diagnostic. It will report exact statuses and resource limits, not select a favorable score or claim scaling beyond these synthetic finite models.

No speedup claim will be made for that code-identical comparison.

## Frozen family matrix

All cases use the strict version-1 `orchlang-request-graph` and `orchlang-finite-outcome-kernel` JSON schemas. Each row has a fixed public store and explicit secret scenarios. Exact trace analysis is paired with fresh independent replay of every complete producer report. The finite strong-probabilistic-bisimulation analyzer and its replay are also run where a complete certificate exists, to retain the sufficient-proof/inconclusive distinction. An UNKNOWN producer report has no certificate to replay; a fresh replay worker records that limitation as a status, never as zero time.

The unequal family has two secret routes, `A; C` and `B; C`. `A` and `B` have equal visible usage. A finite history window of one selects different rational point-mass outcomes for `C`, producing a length-two ordered usage witness. The exact producer's inequality report must independently replay as a verified witness. The precision family is the established response-conditioned construction: both starts have the same finite ordered visible law, but their hidden result dependence prevents strong bisimulation from relating their initial states. Exact equality must replay independently; bisimulation remains `inconclusive`, not a counterexample.

## Kernel and observer assumptions

Every kernel is finite and rational, first-match with contract defaults, and only successful outcomes are present. Responses update declared mutable text registers and the complete event history. History-dependent cases match exact prior event records (resolved contract, saturated contract ordinal, template, ordered arguments, response, input usage, output usage); the declared window is at most three events. Productive cycles use the implementation's documented contract-ordinal saturation at 33 and a zero-length history window, yielding a finite reachable system. No case infers provider probabilities or models errors, retries, currency, cumulative execution resources, termination probability, or infinite-run cost.

The exact analyzer decides equality or returns an exact finite witness by the established weighted-automaton row-span method over the finite rational model. The bisimulation analyzer is only a sufficient all-finite-horizon proof; a split is inconclusive. These are applications of established methods, not a new equivalence algorithm: Kiefer et al.'s primary work gives language-equivalence results for probabilistic automata ([CAV 2011 paper](https://people.cs.ox.ac.uk/joel/publications/langeqprobaut11.pdf)); the rational-weighted-automata treatment specifies the field and finite-state setting relevant to exact span reasoning ([LMCS 2013 paper](https://doi.org/10.2168/LMCS-9(1:8)2013)). Strong probabilistic bisimulation follows the established labelled-transition-system relation of Larsen and Skou ([Information and Computation 1991](https://doi.org/10.1016/0890-5401(91)90030-6)).

## Run and reporting rules

There will be one warmup and five separately spawned measured worker processes per input and implementation/operation. Producer, exact replay, bisimulation producer, and bisimulation replay are separate operations and separate processes. Per-run data retain wall seconds, process high-water RSS bytes, status, diagnostic reason/phase, state/transition/label/rank counts, report and certificate byte sizes, replay matrix/work counts, and every producer/replayer bounded-work counter exposed by that source version. Imports are outside the wall timer; RSS includes interpreter startup and imports. A 20-second per-worker timeout prevents a runaway case. No partial result from a timed-out or UNKNOWN analysis is used as a certificate.

Inputs and source hashes are checked before and after timing. Every graph and kernel pair is immutable for the entire paired run; each case gets distinct graph bytes (including a unique graph name), and different kernel families receive distinct bytes. The primary input JSON is generated by the existing scaling script's unchanged generator. Repetition order is fixed by case ID, with the warmup first and measured repetitions numbered 1–5. Report medians only over complete, matching producer statuses; show all raw samples and UNKNOWN/timeout counts separately. No exclusion or family renaming is permitted after seeing timed results. If the implementation changes, keep this baseline intact and rerun the same frozen inputs in a new results file.

## Primary-source scope

The row-span decision is the standard finite-dimensional linear algebra criterion: all reachable rows `mu A_w` must annihilate the terminal and nonterminal columns; an observed nonzero row yields a finite distinguishing word. Finite closure, exact rational arithmetic, and the declared usage observer are premises. The strong-bisimulation result is sufficient by finite-horizon induction; different initial blocks do not imply different trace laws. The study reports implementation work and RSS for the supplied fixtures only.
